## 3. Critical gotchas you MUST remember

### 3.1 Next.js standalone static assets (RECENTLY FIXED)

`next.config.mjs` uses `output: "standalone"`. The standalone server at `.next/standalone/server.js` does **NOT** automatically receive `.next/static/` or `public/`. You must copy them manually.

This is done in `admin-web/Dockerfile`:

```dockerfile
RUN npm run build \
 && cp -r .next/static .next/standalone/.next/static \
 && cp -r public .next/standalone/public
```

If you change the Dockerfile, preserve these copy lines. Without them, the CSS bundle and all JS chunks return 404 and the site renders as unstyled HTML.

Symptom: page HTML returns 200, but `curl /_next/static/css/*.css` returns 404.

### 3.2 admin-web → control-api network routing

Inside Docker, `localhost:8000` resolves to the admin-web container itself, not control-api. The fix is in `admin-web/app/lib/api.ts`:

```ts
function getApiUrl() {
  return (
    process.env["INTERNAL_API_URL"] ??
    process.env["NEXT_PUBLIC_API_URL"] ??
    "http://localhost:8000"
  );
}
```

`INTERNAL_API_URL=http://control-api:8000` is set in `infra/docker-compose.yml` as both a build arg and a runtime env var. The file is `import "server-only"` so it never ships to the browser.

### 3.3 Reason validation

- `reason.detail` **must be ≥ 20 chars** or the API returns 422.
- Always pass `reason.references` as `[]` (empty array), not omitted, to match the `ReasonInput` model.
- Use one of the 9 enum categories above. `buildReason()` in `admin-web/app/lib/api.ts:51` is the canonical constructor.

### 3.4 Database roles

Postgres has two roles:

- `squad` (owner) — used only for migrations, never by the running app.
- `squad_app` — used by control-api at runtime. Has SELECT on all tables, INSERT/UPDATE only on domain tables, **NO INSERT/UPDATE/DELETE on `revisions`** — revisions are written by a trigger. This is the enforcement that makes the audit trail tamper-proof.

`infra/postgres/init.sql` creates `squad_app`. `control-api/app/sql/*.sql` grants table-level privileges after migrations. Do not grant `squad_app` DDL or revisions-write.

### 3.5 Revisions are append-only

Every mutation triggers an automatic insert into `revisions` via a DB trigger in `control-api/app/sql/001_core_domain.sql`. You never write to revisions directly from Python or from a migration. The `reason_*` columns come from the request payload via `app.revision_utils`.

If a test or a seed script needs to backfill state without creating a revision, it cannot — this is intentional. Work with it.

### 3.6 Sequential Docker rebuild

Always:

```
docker compose -f infra/docker-compose.yml build admin-web
docker compose -f infra/docker-compose.yml up -d admin-web
```

Not parallel. Not `--build` on `up`. If you run them in parallel, the container may start on a previous image while the new one is still being tagged.

## 7. Validation discipline

Before declaring any change done:

1. `docker compose -f infra/docker-compose.yml build <service>` (sequential, not parallel)
2. `docker compose -f infra/docker-compose.yml up -d <service>`
3. `curl` the affected pages and confirm HTTP 200
4. Grep the rendered HTML for the structural markers you expect (class names, entity labels, counts)
5. If it's a mutation path, POST to the backend directly with a valid reason payload and confirm the page re-renders with the new state (the `apiRequest` client uses `cache: "no-store"`)
6. Tail `docker logs` and confirm no errors and no `next start does not work with output: standalone` warnings
7. **For `admin-web`**: verify a `/_next/static/css/*.css` URL returns 200, not just the HTML page — see section 3.1

Only then commit. Commit messages: short present-tense summary line, then a paragraph explaining the *why*, not the *what*. Always include:

```

```

(or whatever attribution is appropriate for the current agent)
