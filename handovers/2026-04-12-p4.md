## 3. Your task: test qwen3.5:35b-a3b as the PM model

The user wants to try `qwen3.5:35b-a3b` (a MoE model — 35B total params, ~3.5B active) instead of `qwen2.5-coder:7b` as the default PM model. The hypothesis is that it produces higher-quality planning output while staying fast due to its sparse architecture.

### What to do

1. Update the default `PM_MODEL` in two places:
   - `workers/app/agents/pm_agent.py` line: `PM_MODEL = os.environ.get("PM_MODEL", "qwen2.5-coder:7b")` → `"qwen3.5:35b-a3b"`
   - `infra/docker-compose.yml` workers env: `PM_MODEL: ${PM_MODEL:-qwen2.5-coder:7b}` → `"qwen3.5:35b-a3b"`

2. Rebuild and restart workers:
   ```bash
   docker compose -f infra/docker-compose.yml build workers
   docker compose -f infra/docker-compose.yml up -d workers
   ```

3. Copy the test file into the container and run the P4 test suite:
   ```bash
   docker cp control-api/tests/test_pm_agent.py squad-control-api:/app/tests/test_pm_agent.py
   docker compose -f infra/docker-compose.yml exec control-api pytest -q tests/test_pm_agent.py -v --tb=short
   ```
   Tests take ~2 minutes if the model is fast. They are skipped if runs don't complete within 120s.

4. **Read the decision_log artifact** from a successful run to verify output quality:
   ```bash
   # get a run ID that's paused
   curl -s http://localhost:8000/api/v1/runs | python3 -m json.tool | grep '"id"'
   # get artifacts for that run
   curl -s http://localhost:8000/api/v1/runs/<RUN_ID>/artifacts | python3 -m json.tool
   # get the decision_log content
   curl -s http://localhost:8000/api/v1/artifacts/<ARTIFACT_ID>/content | python3 -m json.tool
   ```

5. If tests pass and output quality looks good, commit:
   ```
   feat: switch PM model default to qwen3.5:35b-a3b
   ```
   If tests fail or the model is too slow (>120s per run), revert to `qwen2.5-coder:7b` and document why in the commit message.

### What "looks good" means

- `spec.brief_summary` is ≥50 chars and reads like a real project summary (not "this is a spec")
- `spec.milestones` has ≥2 entries with real titles and specific AC
- `tasks` has ≥3 tasks with role, priority, and ≥2 AC each
- `decision_log` entries have real rationale (not "we chose X because we chose X")
- `sanity_check.passed = true` in the decision_log artifact

### If qwen3.5:35b-a3b times out

Ollama may need to unload `qwen3.5:27b` first. Check what's loaded:
```bash
curl -s http://localhost:11434/api/ps | python3 -m json.tool
```

If `qwen3.5:27b` is loaded, it will be evicted when `qwen3.5:35b-a3b` is first called (OLLAMA_MAX_LOADED_MODELS=1). The first run may be slow due to model loading. The second run should be faster. If both timeout, fall back to `qwen2.5-coder:7b`.

## 8. Critical gotchas

1. **Sequential rebuild.** Never `up --build`. Always build first, then up.
2. **Test file copying.** Test files are baked into the control-api image. After editing tests locally, `docker cp` the file into the running container before running pytest.
3. **Ollama is on the host, not in Docker.** Workers reach it via `host.docker.internal:11434` (host-gateway is set in docker-compose). From the host, use `localhost:11434`.
4. **github-svc is optional.** Runs succeed without it. It only affects whether GitHub issues are created.
5. **`reason.detail` must be ≥20 chars.** The backend validates this on all mutations.
6. **Revisions are append-only.** Written by DB trigger. Never write to the `revisions` table directly.
7. **`qwen3.5:27b` may already be loaded.** It uses ~42GB VRAM. When workers load `qwen3.5:35b-a3b`, Ollama will evict it. First call may be slow while it loads the new model.
